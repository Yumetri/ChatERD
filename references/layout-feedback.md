# ERD 배치·가독성 피드백

이 문서는 최초 검수·오류 복구·사용자가 요청한 이미지 검수에서 적용한다. 정상 자동 렌더링 경로에는 매번 PNG 검수와 배치 보정을 요구하지 않는다. 간격 진단은 자동 렌더링에서도 제공되지만 그 수치만으로 검수 통과나 실패를 판정하지 않는다.

이 기준은 그림을 읽는 지침이다. 정규화 규칙이나 모든 ERD의 강제 위계가 아니다. 모든 항목을 이미지와 스키마에서 검토하며 해당하지 않는 항목은 이유와 함께 해당 없음으로 판단한다.

| 기준/적용 조건 | 관찰 기준 | 가능한 조치 | Mermaid 한계 |
|---|---|---|---|
| 위계·방향: 사용자가 기준→상세 또는 선행→후행을 설명했을 때 | 한 방향으로 관계를 따라갈 수 있는가 | LR/TB 등을 비교하고 rankSpacing 조정 | 1:N 자체는 업무 위계가 아니며 위치가 위계를 증명하지 않음 |
| 주제별 그룹화: 업무 영역이 확인된 모델 | 관련 엔티티를 찾기 쉬운가 | 일관된 스타일, 큰 모델의 주제별 상세 뷰 제안 | Mermaid 12 subgraph로 명시한 그룹은 지원; 정확한 위치 강제 불가 |
| 관계 추적: 연결이 많은 모델 | 교차·우회·라벨 겹침·평행선 밀집 때문에 끝점을 혼동하는가 | 방향·nodeSpacing/rankSpacing 비교, 허용된 배치 주석 조정 | 교차 제거·최소 선 간격 보장 불가 |
| 연결 엔티티: 사용자가 연관/중간 테이블로 정의한 경우 | 양쪽 대상과의 연결이 드러나는가 | 가까운 배치를 목표로 방향·간격 비교 | 정확한 가운데 배치 지정 불가; 가짜 관계 추가 금지 |
| 정보 위계: 테이블명·속성·키·관계가 함께 표시될 때 | 각 종류의 정보가 구분되는가 | 엔티티 font-size·색·테두리 | 관계 라벨은 별도 스타일이므로 효과를 별도 확인 |
| 읽기 크기: 긴 이름·한국어·많은 컬럼 | 기본 보기에서 잘림·겹침·지나치게 작은 글씨가 있는가 | 여백·글자 크기·간격 비교, 상세 뷰 제안 | 원본의 컬럼을 임의로 숨기거나 삭제하지 않음 |
| 배치 안정성: 이전 이미지가 존재할 때 | 작은 수정에 전체 구조가 불필요하게 흔들리는가 | 불필요한 설정 변경을 되돌림 | Mermaid는 위치 고정·증분 배치를 보장하지 않음 |

관찰한 엔티티·관계·라벨을 지목하고 **관찰한 문제 → 읽기 어려운 이유 → 가능한 조치 → 남는 한계**로 피드백한다. 실제 이미지 없이 문제를 본 것처럼 말하지 않는다. 컬러만으로 역할을 전달하지 않고 키·라벨을 함께 읽을 수 있는지 확인한다. 주제/위계는 사용자가 설명한 내용에 근거하며, 불명확하면 추정임을 표시하거나 질문한다.

우선순위: 내용 누락·잘림·판독 불가를 먼저 해결하고, 라벨 겹침·관계 추적을 다음으로, 장식과 배치 안정성을 마지막으로 본다. 모든 교차를 실패로 처리하지 않는다. 지원되지 않는 조치는 제안으로 남기고 자동 적용하지 않는다. 뷰어의 상세 보기는 원본을 바꾸지 않는다. 별도 원본 파일 생성이나 컬럼 숨김은 사용자 요청이 있어야 한다.

ChatERD 뷰어 확장에서는 `%% @db-camp-layout`으로 수동 테이블 좌표·연결 면·경유점을 보존할 수 있다. 위 표의 정확한 위치 제한은 일반 Mermaid 자동 배치에 대한 설명이다. 이 확장은 [메타데이터 문서](schema-metadata.md)의 범위에서만 적용한다. 기존 수동 배치를 사용자 지시 없이 지우지 않는다. 화면 모드는 기존 주제 그룹과 방향 후보를 비교하며 모든 관계를 업무 위계로 해석하지 않는다. 경로는 직각과 크로우풋 32px 공간을 유지하고, 모든 교차를 제거한다고 주장하지 않는다.

## 관계선 분포

완전히 겹치지 않아도 가까운 평행선은 한 선처럼 보일 수 있다. 같은 통로를 지나가는 관계는 가능한 한 일정한 간격으로 나누고, 빈 공간에 선을 분산한다. 선을 구분할 수 있도록 SVG 원본 좌표의 **24px 간격**을 기본 검수 목표로 삼는다. 사용자가 간격을 지정하면 그 값을 우선한다. 테이블 경계의 고정된 PK/FK 연결점, 크로우풋 구간, 좁은 경유점 주변은 별도로 검토한다. 화면에 맞추며 축소된 경우에는 이미지에서도 구분되는지 확인한다.

`get_preview`의 `layout_feedback`은 그 PNG와 같은 렌더 좌표에서 서로 다른 관계의 평행 구간을 측정한다. 기호용 첫·마지막 구간을 제외하고, 기본적으로 48px 이상 나란히 달리는 선 중 간격이 24px 미만인 구간을 보고한다. `close_parallel_segments`의 관계명·`placement_key`·구간 좌표·`gap_px`·`parallel_run_px`를 PNG와 함께 확인한다. 결과는 최대 20구간이며 `truncated`가 참이면 전체를 검토했다고 주장하지 않는다. `available:false`는 측정 불가이고, `closest_parallel_gap_px:null`은 비교할 긴 평행 구간이 없다는 뜻이다. 0건이어도 짧은 구간·기호·테이블 테두리와의 밀집까지 통과한 것은 아니다.

draw에서 허용된 배치 보정은 다음 순서로 검토한다.

1. 선이 몰린 통로와 관련 테이블을 찾고 현재 PNG를 기준으로 실제 문제를 지목한다. 저장된 그림을 새 렌더러의 결과라고 가정하지 않는다. 보정 후보를 새로 렌더링하고 그 후보의 PNG·수치를 비교한다.
2. 통로에 공간이 부족하면 관련 테이블 사이 간격을 넓힌다. `config.er.nodeSpacing/rankSpacing`과 실제 배치 모드를 함께 확인한다. `@db-camp-layout.mode`가 있으면 `direction`만 바꿔도 방향이 바뀐다고 가정하지 않는다. 화면 모드의 포장 배치는 모든 frontmatter 간격을 그대로 따르지 않으므로 설정 숫자만 늘리고 개선됐다고 판단하지 않는다.
3. 공간이 확보됐는데도 선이 붙으면 영향을 받는 관계의 `edges[placement_key].via`를 서로 다른 통로로 분산한다. 사용자 요청에 배치 조정이 포함될 때만 관련 `nodes` 좌표·연결 면도 조정한다. 바꾸지 않는 수동 설정은 보존하며, PK/FK 대응 행·직각 경로·기호 공간을 유지한다. `via`는 관계마다 한 점만 지원하므로 여러 구간을 임의로 꺾는 형식을 만들지 않는다.
4. PNG와 측정 결과를 다시 확인한다. 긴 선의 공유, 거의 붙은 평행선, 기호·라벨 겹침, 과도한 우회, 전체 축소로 인한 글씨 크기를 함께 비교한다. 밀집만 해결하려고 지나치게 넓은 배치를 선택하지 않는다.

`edgeSpacing`·`lineGap` 같은 지원되지 않는 속성을 원본에 추가하거나 가짜 관계·엔티티로 간격을 만들지 않는다. 24px은 검수 목표이며 현재 렌더러의 최소 간격 제약이 아니다. 지원되는 설정과 최대 2회 보정으로 해결할 수 없으면 남는 관계·간격·읽기 영향을 보고한다. 끝점을 추적할 수 없거나 기호·라벨을 혼동하는 결과는 검수 통과로 저장하지 않는다. discuss는 이 기준으로 관찰과 조정안을 설명하며 배치 주석을 수정하지 않는다.

## 근거와 적용 범위
- [yWorks Layered Graph Layout](https://www.yworks.com/pages/layered-graph-layout.html): 방향 있는 계층 배치, 교차 감소, 라벨 겹침 방지, 그룹, 기존 배치 인지 유지. 이 문서의 yFiles 기능을 Mermaid 지원 기능으로 가정하지 않는다.
- [Graphviz dot](https://graphviz.org/docs/layouts/dot/): 일관된 방향, 교차와 선 길이 감소. 엔진을 교체하는 지침은 아니다.
- [Oracle Data Modeler — Logical Diagram and Subviews](https://docs.oracle.com/en/database/oracle/sql-developer-data-modeler/22.2/dmdug/data-modeler-concepts-usage.html): 복잡한 모델의 주제별 하위 뷰. Mermaid 원본을 임의 분할하지 않는다.
- [Mermaid ERD 문서](https://mermaid.js.org/syntax/entityRelationshipDiagram.html): Crow's Foot, PK/FK/UK, 별칭, nullable, subgraph. 이 앱은 Mermaid 12 파서를 사용하고 SVG와 ELK 배치는 자체 구현한다.
- [ELK Layered 문서](https://eclipse.dev/elk/reference/algorithms/org-eclipse-elk-layered.html): 계층 배치와 그룹·연결선 처리. 정확한 위치나 교차 제거 보장이 아니다.

연결 엔티티의 근접 배치와 정보 위계는 위 시각화 원칙을 ERD 연습에 적용한 검토 지침이며, 보편적 DB 설계 표준이라는 주장은 아니다. 소스 확인: 2026-10-02.
